# Computational Analysis of Psalms (app)

A single-page app, built with Vite + TypeScript + D3: one HTML entry, one
client-side router (`src/lib/router.ts`), and two mountable pages
(`src/pages/comparePage.ts`, `src/pages/clusterPage.ts`) that share one
psalm-picker/detail-panel component family. Navigating between Compare and
Cluster swaps the center panel in place — no full page reload. Reads
`public/data/similarity.json` and `public/data/clustering.json`, both
generated by the `pipeline/` package — run that first if either file is
missing.

## Compare (`/compare/`, `src/pages/comparePage.ts`)

A bare `/` load is immediately canonicalized to `/compare/` (`main.ts`
rewrites the URL via `history.replaceState` before mounting - see
`lib/router.ts`), so the address bar always reflects an actual route.

Psalm-to-psalm pairwise similarity. A method dropdown in the header
switches between every similarity method the pipeline exports (eleven
today, across the lexical, syntactic, and clause-structure families - see
the top-level `README.md`); two views render whichever method is selected:

- **Similarity Matrix** — a 150x150 canvas heatmap, colored by a sequential
  Turbo color scale, with book-boundary guides, hover tooltips, and
  click-to-select.
- **Network Graph** — a D3 force-directed graph; an adjustable threshold
  slider controls which psalm pairs are drawn as edges, nodes are colored by
  the traditional five-book division of the Psalter. The default threshold
  is picked per method (98th percentile of that method's own score
  distribution — see `lib/matrix.ts`'s `percentileOffDiagonal`), since
  different methods have very different baseline similarity.

Selecting a psalm (via the grid, either visualization, or the jump-to-psalm
field) populates the detail panel: incipit, stats, top distinctive terms for
the selected method, and a ranked list of the most similar psalms with the
shared terms that explain each match. Switching methods keeps the selected
psalm and re-renders everything against the new method's data.

## Cluster (`/cluster/`, `src/pages/clusterPage.ts`)

Unsupervised partitioning of the whole Psalter, one similarity signal at a
time — a genuinely different result shape (a partition of 150 psalms into
groups) than Compare's pairwise matrix, so it gets its own route rather than
a third view bolted onto the same one. A method dropdown switches between
spectral clustering runs over each of the same eleven similarity signals,
using the *same* feature names as Compare's dropdown (`lib/featureNames.ts`
is the shared source of truth, so the two pages can never drift out of
sync). The six syntactic/clause-structure signals are validated against
Gunkel's form-critical genre exemplars (`pipeline/ground_truth.py`); the
five lexical/vocabulary signals produce *thematic* clusters instead (which
words/names a group of psalms share) — the method description states
explicitly which kind of grouping the selected signal produces.

The picker panel is identical to Compare's, including its **Color by**
dropdown (Books / Gunkel Genres (6) / Gunkel Genres (14) -
`lib/referenceColor.ts`): this is the one place color ever changes meaning
on either page, and it's the *only* place - cluster assignment is never a
color, since a reader would otherwise be unable to tell whether a color
meant "this signal's cluster" or "the ground truth category." Two tabbed
views render whichever method is selected:

- **Scatter Plot** (`viz/scatterPlot.ts`) — a classical-MDS 2D layout of
  the selected signal's own similarity matrix (`pipeline/embedding.py`):
  psalms this signal treats as similar sit close together, positioned
  independent of cluster or category. Points are colored by the shared
  Books/Gunkel choice; cluster membership is shown structurally instead, as
  a translucent convex hull traced around each cluster's points (a dashed
  ring for clusters under 3 points, since a hull needs at least 3).
  Selecting a psalm dims every point/hull outside its own cluster, and
  clicking empty background (not a hull, not a point - hulls are
  `pointer-events: none`) clears the selection.
- **Genre Alignment** (`components/genreAlignmentMatrix.ts`) — a
  contingency table cross-tabulating the selected clustering against
  Hermann Gunkel's own psalm-by-psalm genre classification
  (`pipeline/gunkel_genre_index.py`), at whichever granularity the shared
  Color-by dropdown is on (6 families or 14 genres - Books has no Gunkel
  granularity of its own, so it falls back to the 14-genre table). Rows are
  Gunkel categories; columns are this signal's clusters, reordered and
  captioned by the category each cluster overlaps with most
  (`lib/clusterColumnOrder.ts`, driven by the pipeline's Hungarian-algorithm
  matching) rather than shown under a bare, arbitrary index number - a
  column with no strong match reads "no strong match" instead of guessing.
  A cell's shade is the row-normalized share of that category's psalms
  landing in that cluster (a legend strip spells out the light-to-dark
  mapping directly), and the cell for the selected psalm's own category and
  cluster is outlined. Above the table, a purity/NMI/ARI summary reports
  label-independent external validation scores - the defensible numbers for
  "how well does this signal recover Gunkel's genres," since (unlike the
  column captions) they don't depend on any particular cluster-to-category
  assignment. Both tabs remount when the signal or the color-by mode
  changes.

The detail panel (`components/clusterDetailPanel.ts`) shows a selected
psalm's cluster and the incipits of every other member.

Two earlier visualizations here (a cluster-sorted similarity matrix, a
cross-signal agreement matrix, and later a cluster-grouped psalm grid) were
built, reviewed, and removed in favor of the scatter plot and the
genre-alignment table above - real data each time, but none delivered a
legible "aha" moment on sight. The generic `viz/matrixHeatmap.ts` primitive
the first two were built on stayed, since Compare's own heatmap is a thin
wrapper around it.

`/genre/` (this page's URL before the Cluster/Genre rebrand) still exists as
a permanent redirect to `/cluster/`, so old links and bookmarks keep
working - a small, hand-maintained static file at repo-root `genre/index.html`
(the same "outside the Vite build" pattern as repo-root `about/`), not
generated by `app/`'s build.

## Development

```bash
npm install
npm run dev      # dev server
npm test         # vitest unit tests (pure logic: ranking, network-graph
                  # construction, color scales, state stores, data loading)
npm run lint
npx tsc --noEmit
npm run build     # production build straight to the repo root (see vite.config.ts)
```

`app/index.html` is the single Vite source entry — it only runs under
`npm run dev` (module imports, `import.meta.env`, etc. are unbundled), and
isn't servable as a plain static file. `npm run build` writes the real
deployable site straight to the repo root (`index.html`, `assets/`,
`data/`) — a *single* built `index.html` serves both routes, since Compare
and Cluster are both client-side routes into the same SPA (see
`src/lib/router.ts`). A direct or refreshed load of `/cluster/` therefore
depends on the host falling back to `index.html` instead of 404ing — see
the top-level README's Deployment section for the Cloudflare config that
does this. Repo-root `genre/index.html` (the redirect stub above) is
untouched by this build, same as `about/`.

## Architecture

```
src/
  types.ts                    JSON payload shapes (mirror the pipeline's two exports)
  lib/                        pure, unit-tested logic
    router.ts                    location.pathname <-> Route ("compare" | "cluster")
    mountGuard.ts                 turn-based staleness check guarding against a
                                 superseded page's in-flight fetch wiring itself
                                 onto whichever page's DOM is now displayed
    pageController.ts            the PageController interface ({ unmount() })
                                 every mount*Page function returns
    dom.ts                      requireEl<T>(selector) - shared by both pages
    featureNames.ts              canonical signal names - shared by both dropdowns
    books.ts                    traditional five-book division + book boundaries
    referenceColor.ts            the shared Books/Gunkel-family/Gunkel-genre color
                                 mode both pages' pickers use (never cluster assignment)
    colorScale.ts                validated categorical hue sequences (books, Gunkel
                                 families/genres) + the similarity (Turbo) and
                                 genre-alignment (accent-hue) sequential scales
    ranking.ts                  top-N similar psalms (Compare)
    network.ts                  threshold -> {nodes, edges}, + selection-dim
                                 predicates (Compare's force graph)
    scatterPlot.ts               embedding -> points, + selection-dim predicates
                                 (Cluster's scatter plot)
    matrix.ts                   matrix statistics (Compare)
    clusterColumnOrder.ts        orders/labels alignment-table columns by matched
                                 category (Cluster)
    alignmentCell.ts             genre-alignment cell/share math + which alignment
                                 table and cell to show for the current selection
                                 (Cluster)
  state/
    store.ts                    Compare's observable store (selected psalm, view, threshold)
    clusterStore.ts              Cluster's observable store (selected psalm, selected
                                 signal, color mode, active tab)
  data/
    loadSimilarityData.ts        fetch + validate similarity.json
    loadClusteringData.ts        fetch + validate clustering.json
    loadGunkelData.ts            fetch + validate gunkel.json (shared reference data)
  viz/
    matrixHeatmap.ts              generic NxN canvas heatmap: arbitrary order/matrix/color
                                 scale/boundaries/tooltip - Compare's only user today, but
                                 kept generic since other Cluster-page visualizations were
                                 already built and removed on top of it (see below)
    heatmap.ts                    Compare's book-ordered similarity heatmap, a thin wrapper
                                 around matrixHeatmap.ts
    network.ts                    Compare's force-directed graph (D3 rendering; graph
                                 construction and selection logic live in lib/network.ts)
    scatterPlot.ts               Cluster's MDS scatter plot with per-cluster hull
                                 outlines (D3 rendering; point/selection logic lives
                                 in lib/scatterPlot.ts)
  components/
    psalmGrid.ts                 low-level grid, parameterized by a colorOf callback
    psalmPicker.ts                the picker grid + legend, shared identically by
                                 both pages - `coloring` is the only thing that varies
    detailPanel.ts                Compare's ranked-matches detail panel
    clusterDetailPanel.ts         Cluster's cluster-members detail panel
    genreAlignmentMatrix.ts       Cluster's Gunkel genre/family-alignment contingency
                                 table (rendering only; see lib/alignmentCell.ts)
    referenceColorSelect.ts       the shared Books/Gunkel-6/Gunkel-14 dropdown
    loadError.ts                  shared "could not load data" error state for both
                                 pages' main()
  pages/
    comparePage.ts               mountComparePage(root, isStale) - Compare's HTML
                                 skeleton + data fetch + all its wiring
    clusterPage.ts                mountClusterPage(root, isStale) - same for Cluster
                                 (loads clustering.json + gunkel.json)
  main.ts                      SPA shell: claims #app, wires the router
                                 (lib/router.ts) and the mount guard
                                 (lib/mountGuard.ts) to mount/unmount
                                 pages/comparePage.ts and pages/clusterPage.ts
                                 on navigation, no full page reload
```

Compare and Cluster are routes within one SPA, not separate HTML entries:
`main.ts` mounts whichever of `pages/comparePage.ts` /
`pages/clusterPage.ts` matches the current URL into the shared `#app` root,
and swaps between them on navigation via `lib/router.ts` (URL <-> route)
and `lib/mountGuard.ts` (so a navigation away mid-fetch can't let its
now-stale data wire itself onto the DOM of whichever page is displayed by
the time it resolves). Each page function renders its own full HTML
skeleton synchronously on mount (so navigating never shows a blank panel
while data loads) and returns a `PageController` whose `unmount()` releases
everything it owns - store subscription, D3 force simulation,
`ResizeObserver`s - since these no longer get torn down for free by a full
page reload.

`matrixHeatmap.ts` is the generic canvas-heatmap primitive Compare's own
heatmap is built on. `psalmGrid.ts`/`psalmPicker.ts` are fully shared
between the two pages now (not page-specific wrappers) - only the
`ReferenceColoring` passed in ever differs. `clusterStore.ts` is
deliberately a smaller, separate store rather than a generalized version of
`store.ts`, since the two pages' state shapes only overlap on
`selectedPsalm` and `referenceColorMode`. `network.ts` and `scatterPlot.ts`
both split into a `lib/` half (pure, unit-tested: graph/point construction,
selection-dimming predicates) and a `viz/` half (the D3/DOM rendering that
calls into it) - the same split, applied consistently to both of the app's
two interactive graphics. `genreAlignmentMatrix.ts` renders a plain DOM
`<table>`, not a canvas heatmap - at up to 14 rows x up to 6-22 cluster
columns it's small enough that real DOM text (crisp labels, native `title`
tooltips) beats canvas raster text for legibility; its cell math and
selection logic live in `lib/alignmentCell.ts`, tested independently of the
DOM construction.
